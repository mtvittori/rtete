# Interface languages (i18n)

The UI (TUI and GUI) is available in Italian and English. The scheme in
`src/i18n.rs` is deliberately minimal: **the Italian text written in the code
is the key**. With Italian selected, strings are returned as-is; with English,
they are looked up in `locales/en.txt`. This is unrelated to
[message translation](translation.md), which translates chat content through an
external service.

## API

- `tr(it: &'static str) -> &'static str` — the string in the current language,
  or the Italian original if no translation exists.
- `trf!("inoltro a {}…", nome)` — exported macro: translate the template with
  `tr`, then fill each `{}` in order via `i18n::fill` (no positional or named
  arguments, no format specs). Extra `{}` without an argument are dropped.
- Locale helpers: `weekdays()`, `months()`, `decimal_sep()` (`,` in Italian,
  `.` in English; used by `model::fmt_size`).
- `rondine::tr` is re-exported at the crate root.

The current language is a process-wide `AtomicU8` set once with
`i18n::set(lang)`.

## Language selection

- `detect()` reads `LC_ALL`, `LC_MESSAGES`, then `LANG` (first non-empty) and
  picks Italian only if the value starts with `it`; anything else, including
  unset, means English.
- The TUI calls `i18n::set(i18n::detect())` at startup.
- The GUI reads `Settings::lang` (`LangChoice(Option<Lang>)`, stored as
  `lingua = auto|it|en` in `gui.conf`) and resolves `None` to `detect()`. It is
  changed in *Settings → Appearance*.

## Locale file format

`locales/en.txt` is embedded with `include_str!`, so translations are compiled
into the binary and need no runtime files. Format:

```
# comment lines start with '#'

testo italiano dal codice
English translation

inoltro a {}…
forwarding to {}…
```

- Blocks are separated by a blank line; inside a block the first non-comment
  line is the key and the second the translation.
- `\n` in either line is unescaped to a newline.
- The parsed map is built lazily once (`OnceLock`).

## Completeness test

`ogni_testo_ha_la_traduzione_inglese` (in `i18n.rs`) walks every `.rs` file
under `src/` (except `i18n.rs` itself), extracts the string literal after each
whole-word `tr(` or `trf!(` — including when the literal starts on the next
line — and fails if:

- a key has no English translation (lists the missing keys);
- a key and its translation have a different number of `{}` placeholders;
- `en.txt` contains translations no longer used in the code.

So every UI string change requires updating `locales/en.txt` in the same
commit; `cargo test` reports what is missing. Strings built dynamically or not
passed literally to `tr`/`trf!` (e.g. emoji-only labels, `"Media"`, `"Link"`)
are not translated.

## Adding a language

The README describes it as "a new file and an entry in `src/i18n.rs`". In
practice that means:

1. add `locales/<code>.txt`;
2. add a variant to `Lang`, to `Lang::ALL`, `name()`, `code()`, and to the
   `lang()` decoding of the atomic;
3. add an `include_str!` constant and a branch in `table()`;
4. extend `weekdays()`, `months()`, `decimal_sep()`;
5. extend the test to check the new table.

See [Testing](../testing/unit-tests.md) for running the suite.
